# M6 — 성능·리소스 측정 및 한계 분석

ZCU102(XCZU9EG)에 Coral NPU(CoreMiniAxi)를 올려 베어메탈로 추론을 동작시킨 결과에 대한 측정과 한계 분석.

## 1. 리소스 사용량

Vivado Implementation(impl_1) 기준. 대상 칩 XCZU9EG.

| 자원 | 사용 | 전체(XCZU9EG) | 사용률 |
|---|---|---|---|
| CLB LUT | 51,105 | 274,080 | 18.6% |
| CLB FF | 17,489 | 548,160 | 3.2% |
| Block RAM (36Kb) | 10 | 912 | 1.1% |
| DSP48E2 | 6 | 2,520 | 0.24% |
| UltraRAM | 0 | 0 | — |

- 위 수치는 NPU 코어(coral_axi_wrapper) + AXI SmartConnect ×2 + Processor Reset 를 포함한 PL 전체 값이다. PS(ARM)는 하드 IP로 PL 자원을 쓰지 않는다.
- M3 단독 합성 시 CoreMiniAxi 코어 자체도 LUT 약 18% 수준으로, NPU 코어가 사용량의 대부분을 차지한다.
- **BRAM 10개 ≈ ITCM 8KB + DTCM 32KB** 사양과 일치.
- **DSP 6개**만 사용 → 곱셈/MAC 연산이 DSP48E2 하드 곱셈기가 아니라 LUT 로직으로 구현되었음을 시사한다(아래 3절 참조).

## 2. 타이밍·클럭

- 초기 100MHz에서 타이밍 위반(WNS -2.385ns, TNS -3363ns).
- PL 클럭을 **50MHz로 하향** → **WNS +0.462ns, TNS 0** 으로 타이밍 통과.
- 즉 현재 구성의 안정 동작 상한은 50MHz 부근이며, 그 이상은 재타이밍/리타이밍 최적화가 필요하다.

## 3. 성능 (실행 명령어 수)

RV32 명령어 실행 수를 사이클 정확 에뮬레이션으로 측정.

| 워크로드 | 동적 명령어 수 | 50MHz·CPI=1 이상적 하한 |
|---|---|---|
| scalar 데모 (output = input×3) | 8 | 0.16 µs |
| FC 레이어 (Y = ReLU(W·X + b), 4×4) | 541 | 10.8 µs |

- FC 레이어는 4개 출력 × 4개 입력 = **16회 MAC**을 수행한다.
- 참고: 아래 541 명령어는 초기에 곱셈을 소프트웨어(shift+add)로 구현한 버전 기준이다. 이후 mul(하드웨어 곱셈)이 정상 동작함을 확인했으므로(4-1절), mul 버전에서는 명령어 수가 크게 줄어든다.
- 실제 하드웨어 사이클은 파이프라인 stall/메모리 대기로 위 하한보다 크다. CPI=1은 이상적 하한이다.


## 3-1. MNIST 손글씨 인식 (실제 학습 모델 + int8 양자화)

임의 가중치 데모를 넘어 실제 학습된 모델을 양자화해 NPU에서 추론한 결과.

**모델**: scikit-learn digits(8x8 손글씨) 학습, 구조 64 → 32(ReLU) → 10, 파라미터 2,410개

| 항목 | float32 | int8 양자화 |
|---|---|---|
| 테스트 정확도(450샘플) | 98.00% | **98.00%** |
| 가중치 메모리 | 9,640 B | **2,368 B (4.0배 절감)** |

- 대칭 양자화(scale = max|r|/127), 누적 int32, 층간 재양자화는 고정소수점 배율 `(a*1792)>>20`.
- **정확도 손실 0** — 이 규모의 MLP에서는 int8이 충분함을 실측으로 확인.

**추론 성능** (에뮬레이션 기준 동적 명령어 수)

| 항목 | 값 |
|---|---|
| 추론 1회 명령어 수 | 17,230 |
| MAC 연산 수 | 2,368 (64×32 + 32×10) |
| MAC당 명령어 | 7.28 |
| 50MHz·CPI=1 이상적 하한 | 345 µs (초당 약 2,900회) |

- MAC당 7.28 명령어는 개선 여지가 크다. 현재 가중치를 int32 배열로 DTCM에 두어 워드 단위
  로드가 많고, scalar 경로만 사용하기 때문이다.
- 개선 방향: (1) int8 패킹 로드로 메모리 트래픽 감소, (2) 벡터(RVV) 유닛 활성화 시 MAC 병렬화,
  (3) 루프 언롤링.

**보드 검증**: 0~9 각 1장씩 10개 샘플을 UART로 그림 출력 + NPU 추론 → **10/10 정확**.


## 3-2. CNN (합성곱 신경망) 실행 및 FC 대비 비교

Conv(8ch 3×3) → ReLU → MaxPool(2×2) → FC(10) 구조를 동일 파이프라인으로 NPU에서 실행.

| 모델 | 파라미터 | 가중치(int8) | 정확도(float32→int8) | 추론 1회 명령어 | MAC당 명령어 |
|---|---|---|---|---|---|
| FC 64-32-10 | 2,410 | 2,368 B | 98.00% → 98.00% | 17,230 | 7.28 |
| CNN 8ch 3×3 | 810 | 864 B | 96.89% → 96.89% | 34,920 | 10.54 |

- **메모리/연산 트레이드오프**: CNN은 가중치 공유로 파라미터가 1/3이지만, 같은 커널을 여러 위치에
  반복 적용하므로 연산량은 약 2배. 임베디드 환경에서 어느 쪽이 유리한지는 메모리 제약과
  연산 성능 중 무엇이 병목인지에 따라 갈린다.
- 두 모델 모두 **int8 양자화 정확도 손실 0**.

**스택 초기화 이슈 (중요)**
- FC 모델은 스택 미사용으로 동작했으나, CNN은 지역변수가 많아 스택을 사용한다.
- 스택 포인터 초기값이 0이어서 `sp-64`가 0xFFFFFFC0으로 언더플로우 → 잘못된 주소 접근으로 코어 정지.
- 시작 코드(start.S)에서 sp를 스크래치 영역 상단(0x17000)으로 초기화하여 해결.
- 시사점: NPU에 복잡한 프로그램을 올릴 때는 런타임 초기화(스택, 필요시 .data 복사)가 필수다.


## 3-3. 외부 모델(IREE + LeNet-5) 탑재 한계 검증

Coral 에뮬레이터에서 동작하던 `lenet5_coral.elf`의 실제 하드웨어 탑재 가능성을 검증했다.

| 항목 | 요구 | 본 구성 | 배수 |
|---|---|---|---|
| 코드(.text) | 533,728 B | ITCM 8,192 B | **65배 초과** |
| 전체 메모리 | 1,684,320 B | 40,960 B | **41배 초과** |
| 스택 주소 | 0x200000 | DTCM 0x10000–0x18000 | 범위 밖 |
| 벡터 명령 | 0개 | 미지원 | 문제 없음 |

- 용량의 대부분은 모델(약 59 KB)이 아니라 **IREE 런타임**(VM 인터프리터, 수백 KB)이다.
- 보드 실측: ITCM에 코드 일부를 적재하고 read-back 검증 통과 → **AXI 적재 경로는 정상**,
  실패 원인은 접근성이 아니라 **용량**임을 분리 확인.
- 동일 과제(손글씨 분류)를 본 프로젝트의 네이티브 구현은 **440 B**로 수행한다 (약 1,200배 차이).

**시사점**: 에뮬레이션에서의 동작이 하드웨어 동작을 보장하지 않는다. 임베디드 추론에서는
런타임(프레임워크) 오버헤드가 모델 자체보다 클 수 있으며, TCM 수준 메모리에서는
네이티브 구현이 사실상 유일한 선택지가 된다.

## 4. 핵심 한계

### 4-1. 하드웨어 곱셈(M-확장) — 정상 동작 (초기 판단 정정)
- [정정] 초기에는 `mul` 사용 프로그램이 멈춰 "M-확장 미동작"으로 판단했으나, 통제 실험(트랩 핸들러로 mul 예외를 감지)에서 **mul이 정상 동작(6×7=42)** 함을 확인했다. 반복문 내 16회 곱셈을 쓰는 FC(mul 버전)도 재실행 시 정상(Y=[16,0,10,113]).
- 앞선 멈춤은 하드웨어 한계가 아니라 **일시적 실행 상태**(직전 디버그 세션 미종료 등)로 판명됐다.
- 다만 곱셈이 DSP48E2가 아닌 **LUT 로직으로 구현**된 점(DSP 6개만 사용)은 사실이며, 이는 기능이 아니라 **면적·속도 효율** 측면의 특성이다.

### 4-2. 타깃 칩 규모 차이 (가장 큼)
- Coral의 기본 합성 타깃은 xcvu13p(약 3,780K 로직 셀)이고, ZCU102의 ZU9EG는 약 600K로 **약 6배 작다.**
- 대응: SoC 전체가 아닌 **NPU 코어(CoreMiniAxi)만 분리 합성**하여 LUT 18% 수준으로 수용. 이 축소 전략과 근거 자체가 분석 결과물이다.

### 4-3. 벡터(SIMD)·매트릭스 유닛 미활용
- 이번 데모는 scalar 경로만 사용했다. Coral의 강점인 vector(zve32x)/matrix 유닛은 이번 구성/프로그램에서 활용하지 않았다.
- 벡터 유닛 활용 시 MAC 처리량 향상 여지가 있으나, 곱셈기·리소스 제약과 함께 검토가 필요하다.

### 4-4. ZCU102 공식 미지원
- Coral FPGA 흐름은 Google 사내 보드(Nexus) 기준으로, 사내 로더/호스트를 전제한다.
- 대응: AXI 이름 변환 wrapper(coral_axi_wrapper.sv)와 PS↔PL 연결을 직접 작성, bootgen으로 BOOT.bin을 구성해 SD 독립 부팅을 실현.

## 5. 결론
- ZU9EG(목표 대비 1/6 규모)에서 **NPU 코어 분리 합성 → 50MHz 타이밍 확보 → PS↔NPU AXI 연결 → 베어메탈에서 신경망 완전연결층 추론**까지 end-to-end 동작을 확인했다.
- 주요 제약은 (1) 칩 규모, (2) 클럭 상한 50MHz이며, 각각 코어 분리 합성·재타이밍으로 대응 가능하다. 곱셈기는 DSP 아닌 LUT 구현이라 효율 개선 여지가 있다.
- 향후 과제: HW 곱셈기/벡터 유닛 활성화, 실제 하드웨어 사이클 카운터 측정(A53 글로벌 타이머), 더 큰 레이어/모델로 확장.

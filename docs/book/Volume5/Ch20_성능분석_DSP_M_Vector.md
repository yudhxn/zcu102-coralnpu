# Chapter 20. 성능 분석 — Shift+Add · M Extension · DSP · Vector 4중주

> 이 장이 M6의 설계도다. "DSP 6개"라는 하나의 관측에서 출발해, 가설 수립 → 판별 실험 → 개선 로드맵까지.

---

## 20.1 관측 사실 정리

```
[합성 리포트, M3]
  DSP48E2:  6 / 2,520   (0.24%)
  CLB LUT:  ~49,300     (LUT6가 25,975개로 최다)
  BRAM:     10          (TCM과 정합 — 설계 무결성 증거)

[ISA 문자열]
  rv32imf_zve32x_...    (m 존재 = mul 명령 지원 계약)
```

긴장 관계: **NPU + m 지원인데 곱셈 하드웨어(DSP)가 거의 없음.**

## 20.2 가설 트리

```
왜 DSP가 6개인가?
│
├─ H1. GENERIC 경로 가설
│    USE_GENERIC 파라미터가 벤더 중립 구현 선택
│    → 곱셈이 명시적 논리(시프트·가산 구조)로 전개된 Verilog
│    → Vivado가 "곱셈"인 줄 몰라 DSP 추론 실패 (12·18장)
│
├─ H2. 반복형 곱셈기 가설
│    면적 절약을 위해 mul을 수십 클럭 Shift+Add 순차 회로로 구현 (8장 시나리오3)
│    → DSP는 애초에 불필요, 곱셈이 느림
│
└─ H3. Matrix Unit 미포함 가설
     CoreMiniAxi 구성에 Matrix 배열이 빠져 있거나 축소
     → 남은 곱셈원(Scalar mul, 주소계산 등)만 소량 = 6개
```

셋은 배타적이지 않습니다. H3+H1 동시 성립 같은 조합도 가능.

## 20.3 판별 실험 설계

| 실험 | 방법 | H1 | H2 | H3 |
|---|---|---|---|---|
| E1. 생성 Verilog 검색 | CoreMiniAxi.sv에서 `*` 연산자·`assign p = a * b` 패턴 grep | `*` 없음→지지 | — | — |
| E2. mul 사이클 실측 | Verilator에서 mul 명령 전후 사이클 카운터 (rdcycle) | 1~4클럭→H2 기각 | 수십 클럭→지지 | — |
| E3. Chisel 소스 확인 | Matrix Unit 인스턴스가 CoreMiniAxi 계층에 있는지 | — | — | 없음→지지 |
| E4. 합성 계층 리포트 | Vivado의 모듈별 자원 분포 (report_utilization -hierarchical) | 곱셈 모듈의 LUT 비대→지지 | 작은 곱셈 FSM→지지 | Matrix 계층 부재→지지 |

> **E2가 가장 강력합니다.** RISC-V에는 `rdcycle`(사이클 카운터 읽기, zicsr 확장으로 접근)이 있어, 시뮬레이터에서 곱셈 1000회 루프의 사이클을 재면 구현 방식이 수치로 드러납니다. M2에서 미뤄둔 "사이클 측정"이 여기서 결정적 증거가 됩니다.

## 20.4 개선 로드맵 (측정 후 선택)

```
단계 0 (현재): 동작 확인이 최우선. 성능은 기록만.

단계 1 — DSP 활성화:
  · H1이 맞다면: 합성 속성(use_dsp)을 곱셈 모듈에 지정하거나,
    Chisel 파라미터로 벤더 경로 선택 → 재합성 → DSP 수 변화 관측
  · 기대 효과: 임계 경로 단축 → 클럭 상향 여지

단계 2 — M Extension 경로 최적화:
  · H2가 맞다면: 빠른 곱셈기 구성 선택(Chisel 파라미터) 후 면적-속도 재평가

단계 3 — Vector Unit 활성화:
  · zve32x 명령을 실제로 쓰는 커널 작성(컴파일러 intrinsic/어셈블리)
  · 스칼라 대비 speedup 측정 → "SIMD 폭 128b의 실효" 정량화

단계 4 — Coral Full Port:
  · Matrix까지 포함한 구성(H3 해소)을 ZU9EG 자원 한도 내에서 시도
  · LUT 18% → 얼마까지 커지는지가 그 자체로 결과물
```

> **모든 단계는 "안 되어도 결과물"입니다.** 각 단계의 자원·클럭·사이클 변화 표가 곧 분석 보고서의 본문이 됩니다.

## 20.5 성능 지표 설계 (M6 보고서 틀)

| 지표 | 측정법 | 비교 대상 |
|---|---|---|
| 곱셈 지연 (클럭) | rdcycle 루프 (E2) | ARM A53의 mul |
| 추론 1회 사이클 | 시작~DONE 폴링 사이 rdcycle | 시뮬 예측치 |
| 실효 대역폭 | 전송량 ÷ 시간 (master 포트) | HP0 이론치 |
| 자원 효율 | 연산/LUT | 단계별 변화 |

## 요약·퀴즈

- 관측(DSP 6) → 가설 3개(GENERIC 추론실패 / 반복형 곱셈기 / Matrix 미포함) → 판별 실험 4개 → 개선 4단계.
- 최강 증거는 rdcycle 사이클 실측. "명령 지원 ≠ 빠른 실행"(8장)을 수치로 입증하는 도구.
- 분석의 태도: 낮은 DSP 수는 결함이 아니라 **구현 선택의 흔적**이며, 그 규명 자체가 결과물.

**Q (교수님). "DSP를 늘리면 무조건 좋아지나?"**
A. 아닙니다. 곱셈이 임계 경로일 때만 클럭 상향으로 이어지고, 병목이 메모리(AXI/DDR 대역폭)라면 DSP를 늘려도 추론 시간은 그대로입니다. 그래서 사이클 실측으로 병목 위치를 먼저 확정한 뒤 개선 단계를 고르도록 설계했습니다.

# Chapter 9. Pipeline — 같은 회로로 처리량을 몇 배로 (심화판)

---

## 9.1 용어

**Pipeline**
/ˈpaɪp.laɪn/
파이프라인
**명령어 처리를 여러 단계로 나누고, 서로 다른 명령어의 서로 다른 단계를 동시에 진행시키는 구조.**

## 9.2 비유 — 세탁소, 그리고 공장의 역사

빨래 = 세탁기 30분 → 건조기 30분 → 다림질 30분.

```
파이프라인 없음 (빨래 하나씩 순서대로 처리, 기계는 대부분 놀고 있음):
  빨래1: [세탁][건조][다림]
  빨래2:                   [세탁][건조][다림]
  → 빨래 2개 처리에 3시간 소요, 세탁기는 첫 30분만 일하고 90분 놀고 있음

파이프라인 (세탁기·건조기·다리미가 항상 일함):
  빨래1: [세탁][건조][다림]
  빨래2:      [세탁][건조][다림]
  빨래3:           [세탁][건조][다림]
  → 첫 완성 후 30분마다 하나씩! (처리량 3배)
```

**개별 빨래 하나가 완성되는 시간(90분)은 똑같습니다.** 달라진 건 **여러 개를 처리할 때의 평균 속도**입니다. 이 구분이 파이프라인 이해의 핵심입니다.

### 역사적 기원

이 아이디어의 산업적 원형은 헨리 포드의 **컨베이어 벨트 조립 라인**(1913)입니다. 자동차 한 대를 한 명이 처음부터 끝까지 만드는 대신, 공정을 나눠 각 노동자가 한 단계씩 반복하고 차체가 벨트를 타고 이동합니다. CPU 설계자들은 1960년대(IBM System/360)부터 이 원리를 명령어 실행에 적용하기 시작했습니다.

## 9.3 CPU 파이프라인의 구조

2장의 Fetch-Decode-Execute를 **물리적으로 분리된 회로 단계**로 만들고, 단계 사이에 **파이프라인 레지스터**(3장의 FF)를 끼워 결과를 다음 단계로 넘깁니다.

```
클럭:      1    2    3    4    5    6    7
명령A:   [F ][D ][E ][M ][W ]
명령B:        [F ][D ][E ][M ][W ]
명령C:             [F ][D ][E ][M ][W ]
명령D:                  [F ][D ][E ][M ][W ]

F=Fetch  D=Decode  E=Execute  M=Memory access  W=Write-back
→ 클럭 5부터 매 클럭 명령 하나씩 "완성"
```

```
파이프라인 레지스터의 실체

  [Fetch 회로] ──►[FF]──►[Decode 회로]──►[FF]──►[Execute 회로]──►[FF]──►...
                  ▲                      ▲                      ▲
                 clk                    clk                    clk
     각 FF가 "이전 단계의 결과"를 다음 클럭까지 붙들어 준다
```

**Coral은 4단 파이프라인**입니다(README/데이터시트). 정확히 이 그림에서 단이 4개라는 뜻이며, 이상적인 경우 클럭마다 명령 하나가 완성됩니다.

### 부수 효과 — 클럭 주파수도 함께 오른다

단계를 잘게 나누면 **각 FF 사이의 조합 논리(LUT 사슬)가 짧아집니다**(1장 리플 캐리, 13장 타이밍의 원리를 다시 떠올리세요). 짧은 경로는 더 빠른 클럭에도 살아남으므로, 파이프라인은 **처리량과 클럭 주파수를 동시에** 끌어올리는 효과가 있습니다. 단, 무한정 잘게 쪼갤 수는 없습니다 — 아래 해저드가 그 대가입니다.

## 9.4 해저드 — 파이프라인의 세금

**Hazard** /ˈhæzərd/ 해저드 — 파이프라인이 이상적으로 흐르지 못하게 막는 상황. 세 종류가 있습니다.

### ① 데이터 해저드 (Data Hazard)

```
add x3, x1, x2    ← x3의 결과가 아직 Write-back(W) 안 끝남
sub x5, x3, x4    ← 다음 명령이 벌써 x3를 읽으려 함!

클럭:     1    2    3    4    5
add:    [F ][D ][E ][M ][W ]     ← x3는 클럭5에야 레지스터 파일에 확정
sub:         [F ][D ][E ]...      ← 클럭3(Decode)에 x3를 읽으려 하는데 아직 없음!
```

**해결책 — 포워딩(Forwarding/Bypassing)**: Write-back까지 기다리지 않고, ALU 출력을 **곧바로** 다음 명령의 ALU 입력으로 지름길 배선을 냅니다.

```
   add의 Execute 결과 ──────┐
                            ▼ (지름길 배선)
   sub의 Execute 입력 ◄─────┘
   (레지스터 파일을 거치지 않고 바로 전달)
```

포워딩으로도 못 메우는 경우(예: Load 직후 바로 그 값을 쓰는 경우, "load-use hazard")는 **스톨(stall)** — 파이프라인을 한 클럭 멈춰 세웁니다. 낭비지만 안전합니다.

### ② 제어 해저드 (Control Hazard)

```
beq x1, x2, L     ← 이 분기가 성립할지 여부는 Execute 단계에서야 확정
???               ← 그런데 다음 Fetch는 Decode보다도 먼저 벌써 일어나야 함!
                     "L로 가야 하나, 다음 줄로 가야 하나?"
```

**해결책 — 분기 예측(Branch Prediction)**: 결과가 나오기 전에 **추측**으로 먼저 Fetch를 진행합니다. 맞으면 이득, 틀리면 이미 진행한 단계들을 **버리고(flush)** 다시 시작 — 이걸 **분기 오예측 패널티(misprediction penalty)** 라 합니다. 파이프라인이 깊을수록(단이 많을수록) 이 패널티도 커집니다.

### ③ 구조적 해저드 (Structural Hazard)

두 단계가 **같은 하드�웨어 자원**(예: 같은 메모리 포트)을 동시에 쓰려 할 때 발생. 보통 자원을 이중화하거나(예: 명령 메모리와 데이터 메모리를 분리) 조정 로직으로 해결합니다. **Coral의 ITCM/DTCM이 분리된 이유 중 하나**가 바로 이것 — Fetch(명령 읽기)와 Load/Store(데이터 읽기/쓰기)가 같은 클럭에 동시에 일어나도 서로 자원을 다투지 않습니다.

## 9.5 파이프라인 깊이의 트레이드오프

```
얕은 파이프라인 (예: 2~4단)
  + 해저드 빈도·패널티가 작음
  + 회로가 단순 (제어 로직 면적 작음)
  − 클럭 주파수를 크게 못 올림 (한 단계가 여전히 김)

깊은 파이프라인 (예: 15~20단, 고성능 CPU)
  + 클럭 주파수를 매우 높일 수 있음
  − 분기 오예측 패널티가 커짐
  − 포워딩·해저드 감지 로직이 복잡해져 면적 증가
```

Coral이 4단을 택한 것은 **임베디드 NPU의 목표(면적·전력 효율)에 맞춘 절충**입니다. 서버 CPU처럼 깊은 파이프라인으로 극한의 클럭을 노리지 않는 대신, 회로를 작고 예측 가능하게 유지합니다.

## 9.6 현재 프로젝트 연결

- 데이터시트 "4-stage" 문구를 이제 회로 수준(FF로 나뉜 4개 조합 논리 블록)까지 그릴 수 있습니다.
- ITCM/DTCM 분리(4·17장)가 구조적 해저드 회피와도 연결된다는 관점이 이 장에서 새로 추가된 것입니다.
- **20장 성능 분석과의 연결**: `mul`이 여러 클럭 걸리는 구현(H2 가설)이라면, 그 여러 클럭 동안 파이프라인이 스톨될지, 아니면 별도 파이프라인으로 분리돼 뒤 명령이 흘러갈 수 있는지가 실제 처리량에 영향을 줍니다. rdcycle 실측 시 이 스톨 여부도 함께 관찰 대상입니다.

## 요약

- 파이프라인: 단계를 나눠 겹쳐 처리 → 처리량 및 클럭 주파수 동시 상승, 개별 지연은 불변.
- 3대 해저드: 데이터(포워딩/스톨), 제어(분기예측/flush), 구조적(자원 이중화). 각각 대가가 있음.
- Coral의 4단은 면적·전력 우선의 절충 선택.

## 예상 질문

**Q (교수님). "파이프라인을 더 깊게 하면 항상 좋은가?"**
A. 아닙니다. 깊이가 늘수록 분기 오예측 패널티와 해저드 감지 회로의 복잡도가 커져 면적·전력이 증가합니다. 임베디드 NPU처럼 예측 가능한 저전력 동작이 목표라면 얕은 파이프라인이 합리적 선택입니다.

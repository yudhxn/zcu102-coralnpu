# Chapter 10. Out-of-order — 순서를 조금 어겨서 더 빨라지기 (심화판)

---

## 10.1 용어

**Out-of-order execution (OoO)**
/ˌaʊt əv ˈɔːrdər/
아웃 오브 오더 (비순차 실행)
**명령을 프로그램에 적힌 순서와 다르게, 준비된 것부터 실행하는 기법.**

**In-order** /ɪn ˈɔːrdər/ 인 오더 — 순서대로.

## 10.2 비유 — 은행 창구와 식당 주방

### 은행 창구

```
완전 순차(in-order) 처리: 줄 선 순서대로만.
  1번 손님: 복잡한 대출 상담 (30분)
  2번 손님: 단순 입금 (1분)
  → 2번 손님도 31분을 기다려야 함. 억울함.

비순차(out-of-order) 처리: 준비된 용무부터.
  2번 손님의 입금은 옆 창구에서 먼저 처리 (1분 만에 완료)
  1번 손님의 대출은 계속 진행 중 (30분)
  → 전체 대기시간 대폭 감소. 단, "누가 몇 번째로 왔는지" 관리가 복잡해짐(번호표 시스템 필요)
```

### 식당 주방 (병렬성까지 포함한 비유)

```
주문 순서: ①스테이크(15분) ②샐러드(2분) ③커피(1분)

순차 조리: 스테이크 다 굽고 → 샐러드 만들고 → 커피 내림 = 18분 후 전부 나옴

비순차+병렬 조리: 스테이크는 오븐에 넣어두고, 그 사이 샐러드·커피를 먼저 완성
  → 커피 1분 만에 나옴, 샐러드 2분 만에, 스테이크만 15분 걸림
  → 손님은 훨씬 빨리 무언가를 받기 시작함
```

CPU에서 "스테이크"는 **DDR 메모리 접근처럼 오래 걸리는 명령**, "커피"는 **레지스터끼리의 덧셈처럼 순식간에 끝나는 명령**입니다.

## 10.3 완전한 OoO의 구조 — 왜 크고 복잡한가

고성능 서버/PC CPU가 쓰는 완전한 비순차 실행은 다음 부품들을 필요로 합니다.

```
① 명령 발행 큐 (Issue Queue)
     여러 명령을 대기시키며 "준비된 것"을 매 클럭 골라 실행 유닛으로 보냄

② 레지스터 리네이밍 (Register Renaming)
     "x3에 두 번 쓴다"처럼 겹치는 이름을 물리적으로 다른 저장소에 배정
     → 진짜 데이터 의존이 아닌 "이름만 같은" 가짜 의존을 제거

③ 재정렬 버퍼 (Reorder Buffer, ROB)
     실행은 순서가 뒤섞여도, "겉으로 보이는 완료(commit)"는
     반드시 프로그램 순서대로 나가도록 정렬해주는 큐
     → 이게 없으면 예외 처리·분기 오예측 복구가 불가능해짐
```

이 세 부품은 **면적을 크게 잡아먹습니다.** 고성능 CPU에서 이 로직이 코어 면적의 상당 부분을 차지하는 경우도 흔합니다. **임베디드·NPU에는 사치**입니다.

## 10.4 Coral의 절충 — in-order dispatch, out-of-order retire

Coral 데이터시트 문구를 정확히 풀어봅니다: **"4-stage, in-order dispatch / out-of-order retire"**

```
발행(dispatch) : 프로그램에 적힌 순서 그대로 파이프라인에 밀어 넣음
                  → 리네이밍·발행 큐 불필요, 회로 단순

완료(retire)   : 먼저 끝난 것부터 결과를 확정
                  → 느린 명령(메모리 접근 등)이 뒤의 빠른 명령을
                     붙잡아두지 않음
```

예시로 확인:

```
명령1: lw   x5, 0(x10)   ← DDR 접근 경유 시 수십 클럭
명령2: add  x3, x1, x2   ← 1클럭짜리, x5와 무관 (독립적)

완전 순차 완료라면:
  add가 굳이 lw의 완료를 기다려야 함 → 수십 클럭 낭비

Coral의 절충 (OoO retire):
  add가 먼저 완료(retire)됨. lw는 나중에 완료됨  ✅
  단, add와 lw의 "발행 순서"는 원래 순서 그대로 유지됨
```

**핵심 차이**: 완전 OoO는 **발행 순서까지** 뒤섞습니다(위 예시에서 lw보다 add를 먼저 파이프라인에 밀어 넣을 수도 있음). Coral은 **발행은 순서대로, 완료만** 뒤섞입니다. 완전 OoO의 이점 상당 부분(느린 명령이 전체를 막지 않는 것)을 훨씬 **적은 회로 비용으로** 얻는 절충안입니다.

## 10.5 발행 폭 — 4-way scalar, 2-way vector dispatch

데이터시트의 나머지 문구도 해독합니다.

```
4-way scalar dispatch  : 한 클럭에 스칼라 명령을 최대 4개까지 동시 발행
2-way vector dispatch  : 한 클럭에 벡터 명령을 최대 2개까지 동시 발행
```

```
클럭 1:  [스칼라1][스칼라2][스칼라3][스칼라4]   ← 4개 동시 발행
클럭 2:  [스칼라5][벡터1  ][벡터2  ]            ← 스칼라+벡터 섞어서
```

**발행 폭이 넓을수록** 파이프라인의 여러 슬롯이 동시에 채워져 처리량이 늘지만, 그만큼 "이번 클럭에 뭘 몇 개나 동시에 보낼 수 있는지" 판별하는 제어 로직(해저드 검사를 여러 명령 조합에 대해 동시에 수행)이 커집니다. 4-way/2-way는 이 역시 절충점입니다.

## 10.6 현재 프로젝트 연결

- 데이터시트 문장을 완전히 해독: **"4단 파이프라인 + 순서 발행 + 비순서 완료 + 스칼라 4-way/벡터 2-way 발행"**이라는 설계가 우리 눈에 그림으로 그려집니다.
- 이 절충은 **면적(FPGA 자원)과 성능의 타협**입니다. 완전 OoO였다면 리네이밍·ROB 로직 때문에 LUT 사용량이 훨씬 컸을 것이고, ZU9EG 탑재(12장 리소스표의 18%)가 더 빠듯했거나 불가능했을 수 있습니다.
- **20장 성능 분석과의 연결**: `mul`이 여러 클럭 걸리는 구현(H2 가설)이라면, OoO retire 덕분에 그 뒤의 독립적인 명령들이 곱셈 완료를 기다리지 않고 먼저 끝날 수 있습니다. 즉 "곱셈이 느려도 전체 처리량은 생각보다 덜 나빠질 수 있다"는 예측이 이 장에서 가능해집니다 — rdcycle 실측에서 이 효과를 분리해 관찰할 필요가 있습니다.

## 요약

- OoO: 준비된 명령부터 처리해 느린 명령이 전체를 막지 않게 함. 완전한 형태는 리네이밍·ROB 등으로 면적이 큼.
- Coral의 절충: 발행은 순서대로(단순), 완료만 비순차(효과의 상당 부분을 저비용으로 획득).
- 발행 폭(4-way/2-way)은 처리량과 제어 회로 복잡도의 또 다른 트레이드오프.

## 예상 질문

**Q (교수님). "Coral이 완전한 OoO가 아닌 것이 성능에 실제로 얼마나 손해인가?"**
A. 정성적으로는, 발행 순서까지 뒤섞는 완전 OoO만큼 명령어 수준 병렬성(ILP)을 끌어내지는 못합니다. 다만 NPU 워크로드는 컴파일 시점에 접근 패턴이 예측 가능한 경우가 많아(4장 TCM 논의와 연결), 완전 OoO의 이점 자체가 범용 CPU만큼 크지 않을 수 있습니다. 정량적 손해는 실측(사이클 카운트, 20장)으로 확인이 필요한 영역입니다.

# Chapter 2. CPU 구조 — 스스로 명령을 읽는 기계

> 1장의 덧셈기는 "시키는 대로만 하는 부품"이었다. 이 장에서는 **스스로 명령을 읽고, 해석하고, 실행하는 능력**을 붙인다. CPU의 탄생이다.

---

## 2.1 요리사 비유

**CPU**
/ˌsiːpiːˈjuː/
씨피유 (Central Processing Unit, 중앙 처리 장치)
**메모리에서 명령을 하나씩 가져와 해석하고 실행하는 기계.**

레시피(프로그램)를 보고 요리하는 요리사를 상상하세요.

```
레시피 책     = 메모리 (명령어가 순서대로 적혀 있음)
북마크        = PC (Program Counter, 지금 몇 번째 줄인지)
요리사의 눈   = Fetch (명령 읽기)
요리사의 머리 = Decode (명령 해석: "'다진다'가 뭐지?")
요리사의 손   = Execute (실행: 실제로 다진다)
도마 위 재료  = Register (지금 손에 닿는 곳의 재료)
냉장고        = Memory (재료 창고, 가지러 가면 시간이 걸림)
```

## 2.2 폰 노이만 구조 — 프로그램도 데이터다

**Von Neumann Architecture**
/fɒn ˈnɔɪmən/
폰 노이만 구조
**프로그램(명령어)과 데이터를 같은 메모리에 저장하는 구조.** 1945년 수학자 존 폰 노이만이 정리.

### 역사 — 왜 만들어졌는가

ENIAC(1946)은 프로그램을 바꾸려면 **전선을 물리적으로 다시 꽂아야** 했습니다. 며칠 걸리는 작업이었죠. 폰 노이만의 통찰은 단순했습니다:

> **"명령어도 결국 숫자다. 데이터처럼 메모리에 넣어두면 되지 않는가?"**

프로그램 교체 = 메모리 내용 교체. 전선 재배치가 사라졌습니다. 오늘날 거의 모든 컴퓨터(Coral NPU 포함)가 이 구조입니다.

```
┌─────────────────────────────────┐
│           Memory                │
│  ┌───────────┬───────────────┐  │
│  │ 명령어들   │  데이터들      │  │
│  └───────────┴───────────────┘  │
└──────────────┬──────────────────┘
               │ 버스 (읽기/쓰기 통로)
┌──────────────▼──────────────────┐
│            CPU                  │
│  ┌────────┐  ┌──────────────┐  │
│  │Control │  │  Datapath     │  │
│  │(제어)   │  │  ALU+Register │  │
│  └────────┘  └──────────────┘  │
└─────────────────────────────────┘
```

## 2.3 명령어 사이클 — CPU의 심장 박동

CPU가 하는 일은 단 세 동작의 무한 반복입니다.

```
   ┌─────────────────────────────┐
   │                             │
   ▼                             │
 Fetch  ──►  Decode  ──►  Execute┘
 (가져오기)   (해석)       (실행)
```

**Fetch** /fɛtʃ/ 페치 — PC가 가리키는 주소에서 명령어를 읽어온다.
**Decode** /diːˈkoʊd/ 디코드 — 읽어온 비트열이 무슨 명령인지 해석한다. ("이건 덧셈이군. 대상은 레지스터 1번과 2번.")
**Execute** /ˈɛksɪkjuːt/ 엑시큐트 — 해석 결과대로 실행한다. (ALU로 덧셈, 메모리 접근, 분기 등)

실행이 끝나면 **PC를 다음 명령 주소로 증가**시키고 다시 Fetch. 이것이 초당 수억~수십억 번 반복됩니다.

**PC (Program Counter)**
/ˌpiːˈsiː/
피씨 (프로그램 카운터)
**다음에 실행할 명령어의 메모리 주소를 담은 레지스터.** 레시피의 북마크.

분기(branch) 명령은 PC를 강제로 다른 값으로 바꿉니다 — 이것이 if문과 반복문의 정체입니다.

## 2.4 클럭 — 박자를 맞추는 지휘자

**Clock**
/klɒk/
클럭
**회로 전체에 공급되는 일정한 박자 신호.** 모든 동작이 이 박자에 맞춰 진행된다.

```
    1 ┌──┐  ┌──┐  ┌──┐  ┌──┐
      │  │  │  │  │  │  │  │      ← 클럭 신호
    0─┘  └──┘  └──┘  └──┘  └──
      ↑     ↑     ↑     ↑
    상승 에지마다 회로의 상태가 한 걸음 전진
```

### 왜 필요한가

1장에서 배웠듯 **신호 전파에는 시간이 걸립니다** (캐리 전파를 기억하세요). 어떤 부품은 빠르고 어떤 부품은 느립니다. 박자 없이 각자 제멋대로 진행하면, 아직 도착하지 않은 신호를 읽어 엉뚱한 값이 됩니다.

클럭은 이렇게 약속합니다:

> **"다음 박자가 오기 전까지 모든 신호가 도착해 있어야 한다."**

- **클럭 주파수** (예: 100MHz) = 초당 1억 번의 박자 = 박자 하나가 10ns
- 어떤 신호 경로가 10ns보다 오래 걸리면? → **타이밍 위반** (1장 예고 그대로, Volume 2에서 심화)

> **"CPU가 3GHz다" = 심장이 초당 30억 번 뛴다**는 뜻입니다. 박자당 하는 일의 양(명령어 수)은 설계마다 다르므로, 주파수만으로 성능을 비교할 수는 없습니다.

## 2.5 현재 프로젝트 연결

- **Coral NPU의 Scalar Unit이 정확히 이 구조입니다.** RISC-V 명령어를 Fetch(ITCM에서) → Decode → Execute 하는 작은 폰 노이만 기계. "Coral은 프로세서다"라는 말의 실체가 이 장의 내용입니다.
- **Fetch의 대상이 ITCM인 이유**: 레시피 책(명령어 저장소)을 요리사 바로 옆에 두면(1클럭 접근) Fetch가 절대 늦지 않습니다. (Vol.4에서 심화)
- **단일 클럭 설계**: 합성 리포트에서 확인한 `io_aclk` 하나 — Coral 전체가 한 지휘자의 박자로 움직입니다. 지휘자가 여럿이면(멀티 클럭) 박자 넘김(CDC) 문제가 생기는데, 그게 없어 M4 연결이 단순합니다.
- **ZCU102의 PS에도 같은 구조가 4개** 들어 있습니다(Cortex-A53 쿼드코어). 우리 베어메탈 앱은 그중 하나(a53-0)에서 Fetch-Decode-Execute 됩니다.

## 2.6 요약

- CPU = Fetch → Decode → Execute의 무한 반복 기계. PC가 현재 위치를 추적한다.
- 폰 노이만 구조: 명령어도 숫자이므로 데이터와 같은 메모리에 둔다. 프로그램 교체가 메모리 교체로 단순화됐다.
- 클럭은 "다음 박자 전까지 모든 신호 도착"을 강제하는 지휘자. 주파수가 높을수록 빠르지만, 느린 경로가 있으면 타이밍 위반.

## 2.7 예상 질문

**Q1 (교수님). "Coral이 NPU인데 왜 '프로세서'라고 부르나?"**
A. Coral의 Scalar Unit이 폰 노이만 구조의 완전한 명령어 사이클(Fetch-Decode-Execute)을 수행하기 때문입니다. 고정 기능 가속기(NVDLA류)는 레지스터 설정으로 구동되지만, Coral은 메모리(ITCM)에 적재된 RISC-V 프로그램을 스스로 읽어 실행합니다. 그래서 드라이버 대신 컴파일된 바이너리가 필요하고, 베어메탈 운용이 가능합니다.

**Q2. 클럭 주파수를 낮추면 왜 타이밍 위반이 해결되는가?**
A. 주기가 길어져 신호가 도착할 시간 여유(슬랙)가 늘어나기 때문. 10ns(100MHz)에 12ns 경로는 위반이지만, 20ns(50MHz)면 8ns 여유로 통과.

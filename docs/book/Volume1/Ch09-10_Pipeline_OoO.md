# Chapter 9. Pipeline

## 9.1 용어

**Pipeline**
/ˈpaɪp.laɪn/
파이프라인
**명령어 처리를 여러 단계로 나누어, 서로 다른 명령의 서로 다른 단계를 동시에 진행하는 구조.**

## 9.2 비유 — 세탁소

세탁 = 세탁기 30분 → 건조기 30분 → 다림질 30분.

```
파이프라인 없음 (한 번에 한 빨래만):
  빨래1: [세탁][건조][다림]
  빨래2:                [세탁][건조][다림]
  → 빨래 2개에 3시간

파이프라인 (기계를 놀리지 않음):
  빨래1: [세탁][건조][다림]
  빨래2:      [세탁][건조][다림]
  빨래3:           [세탁][건조][다림]
  → 첫 빨래 이후 30분마다 하나씩 완성!
```

**개별 빨래가 빨라진 게 아닙니다** (여전히 90분). **처리량(throughput)** 이 3배가 된 겁니다. 기계 세 대가 항상 일하니까요.

## 9.3 CPU에 적용

2장의 Fetch-Decode-Execute를 단계별 회로로 나누고, 사이에 **레지스터(플립플롭)** 를 끼워 결과를 넘깁니다.

```
클럭:      1    2    3    4    5
명령A:   [F ][D ][E ][M ][W ]
명령B:        [F ][D ][E ][M ][W ]
명령C:             [F ][D ][E ][M ][W ]

F=Fetch  D=Decode  E=Execute  M=Memory  W=Write-back
→ 3클럭째부터 매 클럭 명령 하나씩 완료
```

**Coral은 4-stage 파이프라인**입니다 (데이터시트). 4단이면 이상적으로 매 클럭 1명령 완료.

### 부수 효과 — 클럭도 올라간다

단계를 나누면 **한 클럭에 처리할 회로 길이가 짧아져** 클럭 주기를 줄일 수 있습니다(1장의 캐리 전파 문제 완화). 파이프라인은 처리량과 주파수를 동시에 올리는 셈.

## 9.4 해저드 — 파이프라인의 골칫거리

**Hazard** /ˈhæzərd/ 해저드 — 파이프라인이 순조롭게 못 흐르는 상황.

```
add x3, x1, x2    ← x3가 아직 파이프라인 안에 있는데
sub x5, x3, x4    ← 다음 명령이 벌써 x3를 달라고 함 (데이터 해저드)

beq x1, x2, L     ← 분기 결과가 나올 때까지
???               ← 다음에 뭘 Fetch할지 모름 (제어 해저드)
```

해결책: 결과를 앞 단계로 지름길로 넘기는 **포워딩**, 잠깐 멈추는 **스톨(stall)**, 분기를 미리 찍는 **분기 예측**. 상세 구현은 이 책 범위를 넘지만, "파이프라인은 공짜가 아니고 관리 회로가 붙는다"는 것만 기억하세요.

# Chapter 10. Out-of-order

## 10.1 용어

**Out-of-order (OoO)**
/ˌaʊt əv ˈɔːrdər/
아웃 오브 오더 (비순차 실행)
**명령을 프로그램 순서와 다르게, 준비된 것부터 실행하는 기법.**

**In-order dispatch** — 명령을 **순서대로 발행**(파이프라인에 투입).
**Out-of-order retire** — 완료(은퇴)는 **순서가 뒤바뀔 수 있음**.

## 10.2 비유 — 은행 창구

```
완전 순차: 줄 선 순서대로만 처리.
  앞사람 업무가 30분짜리면 뒤의 1분짜리 손님도 30분 대기.

비순차: 1분짜리 손님을 옆 창구로 먼저 처리.
  전체 대기 시간 감소. 단, 관리(번호표 시스템)가 복잡해짐.
```

## 10.3 Coral의 절충: in-order dispatch / out-of-order retire

완전한 비순차 실행(발행부터 뒤섞음)은 고성능 CPU의 영역인데, **관리 회로가 엄청나게 큽니다** (재정렬 버퍼, 레지스터 리네이밍 등). Coral은 절충합니다:

```
발행(dispatch): 프로그램 순서대로        ← 관리 단순
완료(retire):   먼저 끝난 것부터        ← 느린 명령(메모리 접근, 곱셈)이
                                          빠른 명령을 안 막음
```

예:

```
명령1: lw   x5, 0(x10)   ← DDR 접근, 수십 클럭 걸림
명령2: add  x3, x1, x2   ← 1클럭짜리, x5와 무관

순차 완료라면: add가 lw를 기다림 (수십 클럭 낭비)
OoO retire:   add 먼저 완료. lw는 나중에 완료  ✅
```

병렬성 스펙도 같이 읽어봅시다: **4-way scalar, 2-way vector dispatch** — 한 클럭에 스칼라 명령 최대 4개, 벡터 명령 최대 2개를 발행할 수 있다는 뜻. 발행 폭이 넓을수록 파이프라인들이 꽉 차서 돕니다.

## 10.4 현재 프로젝트 연결

- 데이터시트 문구 "4-stage, in-order dispatch / out-of-order retire"를 이제 완전히 해독할 수 있습니다: **4단 파이프라인 + 순서 발행 + 비순서 완료의 절충 설계.**
- 이 절충은 **면적(FPGA 자원)과 성능의 타협**입니다. 완전 OoO였다면 LUT 사용량이 훨씬 컸을 것이고, ZCU102 탑재가 어려워졌을 수 있어요. "LUT 18%로 들어간" 결과에는 이 설계 철학이 기여하고 있습니다.
- M6에서 사이클을 측정할 때, 메모리 접근(lw가 AXI 타고 DDR까지)과 연산의 겹침(OoO retire 효과)이 수치에 나타날 수 있습니다.

## 요약·질문·퀴즈 (9–10장 통합)

- 파이프라인: 단계를 나눠 겹쳐 돌린다. 개별 명령은 안 빨라지지만 처리량↑ 클럭↑. 해저드라는 관리 비용 존재.
- OoO retire: 느린 명령이 빠른 명령의 완료를 막지 않게 하는 절충. 완전 OoO보다 회로가 훨씬 작다.
- Coral = 4단 파이프 + in-order dispatch + OoO retire + 4-way/2-way 발행.

**Q (교수님). "Coral이 완전한 out-of-order가 아닌 이유는?"**
A. 완전 비순차 실행은 재정렬 버퍼 등 관리 회로 면적이 커서 임베디드 NPU의 면적·전력 목표와 상충합니다. 발행은 순차로 단순화하고 완료만 비순차로 허용하면, 메모리 지연 은폐 효과의 상당 부분을 작은 면적으로 얻을 수 있습니다.

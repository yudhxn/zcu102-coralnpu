## 5.1 용어

**ISA**
/ˌaɪɛsˈeɪ/
아이에스에이 (Instruction Set Architecture, 명령어 집합 구조)
**"이 CPU가 어떤 명령어를 알아듣고, 그 명령어가 무엇을 하는지"를 정의한 규격서.** 하드웨어 제조사와 소프트웨어 개발자 사이의 **계약(contract)**.

## 5.2 비유 — 언어와 방언

CPU를 사람이라 하면 ISA는 그 사람의 모국어입니다.

```
x86        = 영어 (인텔/AMD PC, 서버)
ARM        = 프랑스어 (스마트폰, ZCU102의 PS)
RISC-V     = 에스페란토 (Coral NPU) — 개방형이라 "누구나 배울 수 있는 언어"
```

같은 뜻("두 수를 더해라")도 언어(비트 패턴)가 다르면 못 알아듣습니다. x86용으로 컴파일된 프로그램이 ARM 칩에서 바로 안 도는 이유가 이것이고, 우리가 Coral용 프로그램을 **크로스 컴파일**(x86 PC에서 RISC-V 바이너리 생성)해야 하는 이유입니다.

### 방언 비유 — 같은 언어, 다른 억양

ISA 안에도 확장(6장)에 따라 "방언"이 있습니다. RV32I만 아는 사람은 표준어만, RV32IMF까지 아는 사람은 계산 관련 전문 용어(곱셈, 실수)까지 압니다. **더 많이 아는 사람은 못 알아듣는 사람의 말도 이해합니다** (상위 호환) — RV32IMF 칩은 RV32I 프로그램도 문제없이 돌립니다.

## 5.3 실체 — ISA는 무엇으로 이루어지는가

ISA 문서가 정의하는 항목들:

```
① 명령어 인코딩     : 비트 패턴이 무슨 뜻인가
                       예) 0000000 00010 00001 000 00011 0110011
                          = "x1과 x2를 더해 x3에" (add x3,x1,x2)

② 레지스터 모델      : 몇 개, 몇 비트, 이름
                       예) RV32I는 x0~x31, 각 32비트

③ 메모리 모델        : 주소는 몇 비트, 접근 단위, 정렬 규칙
                       예) 32비트 주소, byte/halfword/word 접근

④ 제어 흐름          : 분기·점프의 규칙
                       예) beq, jal, jalr

⑤ 예외·인터럽트 규칙  : 오류나 외부 신호가 왔을 때의 약속된 동작

⑥ 특권 모드          : 사용자 모드 / 감독자 모드 등의 구분 (RISC-V의 Privileged spec)
```

### 인코딩을 실제로 읽어보기

`add x3, x1, x2`의 32비트가 왜 그 값인지 뜯어봅니다. RV32I R-type 형식:

```
 31        25 24    20 19    15 14  12 11     7 6      0
┌───────────┬────────┬────────┬──────┬────────┬────────┐
│  funct7   │  rs2   │  rs1   │funct3│   rd   │ opcode  │
│ 0000000   │ 00010  │ 00001  │ 000  │ 00011  │0110011  │
└───────────┴────────┴────────┴──────┴────────┴────────┘
   "덧셈"      x2       x1      "산술"   x3      "R형 연산"
```

- `opcode`(하위 7비트) — Decode(2장)가 **가장 먼저** 보는 필드. "이건 R형 산술 명령이군."
- `funct3`+`funct7` — opcode만으로 구분 안 되는 세부 종류(더하기 vs 빼기 vs XOR 등)를 추가로 지정.
- `rs1`, `rs2` — 소스 레지스터 번호(입력). `rd` — 목적지 레지스터 번호(출력).

> **이것이 Decode 회로의 실체입니다.** LUT(Vol.2)로 이 비트 패턴을 보고 "ALU에게 덧셈을 시켜라, x1과 x2를 읽어 x3에 써라"는 제어 신호를 만드는 조합 논리를 짜는 것 — 그게 CPU 설계의 절반입니다.

## 5.4 CISC vs RISC — 역사의 갈림길

**CISC** /sɪsk/ 시스크 (Complex Instruction Set Computer) — 명령어 하나가 복잡한 일을 통째로 수행. 1970년대 주류(x86의 뿌리).

### 왜 CISC가 먼저 나왔나

1970년대엔 **메모리가 극도로 비쌌습니다.** 프로그램을 저장할 공간이 부족하니, "복잡한 일을 짧은 명령 하나로" 압축하는 게 이득이었습니다. 예: x86의 `REP MOVSB` 한 줄이 "배열 전체 복사"를 통째로 처리.

또 당시엔 **어셈블리를 사람이 직접** 많이 짰습니다. 사람 친화적인 고수준 명령이 프로그래밍을 편하게 했죠.

### RISC의 반란 (1980년대)

버클리(David Patterson)와 스탠퍼드(John Hennessy)의 연구진이 실측 데이터를 들고 반박합니다: **"복잡한 명령어의 대부분은 실제 프로그램에서 거의 안 쓰인다."** 컴파일러가 짜는 코드는 단순한 명령의 조합을 선호했습니다.

이들의 제안:

```
RISC 철학 3원칙

① 명령을 단순하게, 종류를 적게
   → Decode 회로가 단순 → 빠르게 만들기 쉬움

② 명령 길이를 고정
   → Fetch가 "몇 바이트를 읽어야 할지" 미리 앎 → 파이프라인(9장)에 유리

③ Load-Store 구조
   → 메모리 접근은 lw/sw뿐, 연산은 레지스터끼리만 → ALU 설계 단순
```

역사의 판정: **RISC 승.** ARM(전 세계 모바일), MIPS, 그리고 RISC-V가 이 계보. x86조차 내부적으로는 CISC 명령을 **마이크로 연산(μop)** 이라는 RISC풍 조각으로 쪼개 실행합니다 — 겉은 CISC, 속은 RISC인 셈.

## 5.5 ISA가 정하는 것 / 안 정하는 것 — "구현의 자유"

이 구분이 8장(M Extension)의 전체 논리 기반이므로 신중히 봅니다.

| ISA가 **정함** (계약, 반드시 지켜야 함) | ISA가 **안 정함** (구현자의 자유) |
|---|---|
| `add` 명령의 비트 패턴 | 그 덧셈기가 리플 캐리인지 캐리 룩어헤드인지 |
| `mul`이 존재한다는 사실 (M 확장 시) | `mul`이 1클럭에 끝나는지 32클럭에 끝나는지 |
| 레지스터가 32개라는 사실 | 레지스터 파일이 물리적으로 몇 개의 포트를 갖는지 |
| 메모리 주소가 32비트라는 사실 | 캐시가 있는지, TCM인지 |
| 분기가 PC를 바꾼다는 규칙 | 분기 예측기가 있는지, 파이프라인이 몇 단인지 |

> **한 문장 요약**: **ISA는 "무엇을 하는가"의 계약이고, "어떻게 빠르게 하는가"는 구현자의 자유다.**
> 이 자유 때문에 같은 프로그램이 저가 마이크로컨트롤러에서도, 슈퍼컴퓨터에서도 (속도만 다르게) 돕니다.

### 검증 — 같은 ISA, 완전히 다른 두 칩

```
칩 A (초소형): RV32I만. 곱셈 없음. LUT 500개.
칩 B (고성능): RV32IMFVC 전부. 하드웨어 곱셈기, 8단 파이프라인. LUT 50,000개.

둘 다 "add x3,x1,x2"를 실행할 수 있다.
칩 B만 "mul x3,x1,x2"를 실행할 수 있다.
같은 프로그램(RV32I 범위 내)을 컴파일 없이 그대로 양쪽에서 실행 가능.
```

## 5.6 현재 프로젝트 연결

- Coral ISA 문자열 `rv32imf_zve32x_zicsr_zifencei_zbb`는 **이 계약서의 목차**입니다. 6장에서 조각별로 해독합니다.
- **20장의 DSP 미스터리가 정확히 5.5절의 구분입니다.** "`m`이 ISA에 있다"(계약 이행) ≠ "곱셈기가 DSP로 빠르게 구현됐다"(구현의 자유). 이 문장을 스스로 만들 수 있으면 5장을 이해한 것입니다.
- R-type 인코딩(5.3절)을 알면, Coral의 Decode 로직이 합성 리포트에서 LUT 몇 개를 차지하는지 대략 가늠할 수 있습니다 — opcode/funct 필드 폭만큼의 조합 논리이므로 면적이 크지 않은 부분입니다.

## 요약

- ISA = HW/SW 계약서. 명령 인코딩·레지스터·메모리·제어흐름·예외·특권모드를 정의.
- CISC(복잡·적은 명령 수)에서 RISC(단순·많은 명령 실행)로 역사가 이동. 메모리가 싸지고 컴파일러가 발전한 결과.
- **ISA는 "무엇을"만 정하고 "얼마나 빠르게"는 구현 자유** — 이것이 이후 모든 성능 분석의 출발점.

## 예상 질문

**Q1 (교수님). "왜 x86 대신 RISC-V를 배워야 하나?"**
A. x86은 사유 ISA로 새 명령어를 마음대로 추가할 수 없지만, RISC-V는 개방형이라 NPU처럼 도메인 특화 확장을 자유롭게 얹을 수 있습니다. 학습 관점에서도 명령 수가 적어 전체 구조를 완전히 파악하기 쉽습니다.

**Q2. "명령어 길이가 고정이면 뭐가 좋은가?"**
A. Fetch 단계에서 다음 명령의 길이를 계산할 필요 없이 PC+4로 바로 다음 주소를 알 수 있어 파이프라인 설계가 단순해집니다. 가변 길이(x86)는 이 예측이 어려워 별도의 길이 디코더가 필요합니다.

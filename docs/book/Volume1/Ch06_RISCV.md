# Chapter 6. RISC-V — 개방형 ISA의 탄생 (심화판)

---

## 6.1 용어와 이름의 유래

**RISC-V**
/ˌrɪsk ˈfaɪv/
리스크 파이브
**2010년 UC 버클리에서 시작된 개방형(free & open) 명령어 집합.** "V"는 버클리 RISC 계보의 다섯 번째(RISC-I~IV는 1980년대 연구용 칩)라는 뜻이자, 확장(Variations/eXtensions)을 로마자 V로 상징한다는 해석도 있습니다.

## 6.2 왜 만들어졌는가 — 세 가지 결핍

2010년 당시 ISA 생태계의 상황:

```
ARM  : 사유. 라이선스비 수천만~수억 원. 명령어를 자기 마음대로 못 바꿈.
x86  : 사유. 인텔·AMD 외에는 사실상 라이선스 자체가 안 나옴.
MIPS : 사유였다가 후에 오픈소스화 (RISC-V보다 늦음, 영향력 제한적)
SPARC: 사유. 오라클 소유.
```

버클리 연구진(Krste Asanović 등)이 새 CPU 연구·교육을 하려는데, **매번 라이선스 문제와 "이 명령어를 바꿔도 되나"라는 제약**에 부딪혔습니다. 결핍은 셋:

1. **자유롭게 배우고 가르칠 ISA가 없다** (교육용)
2. **자유롭게 연구하고 확장할 ISA가 없다** (연구용)
3. **로열티 없이 칩을 만들 ISA가 없다** (산업용)

답은 단순했습니다: **"그럼 우리가 만들고, 영원히 무료로 공개하자."** 2015년 RISC-V Foundation(현 RISC-V International, 스위스 소재 — 특정 국가 정치 리스크 회피 목적도 있음)이 설립되어 표준을 관리합니다.

### ARM의 역사와 대비해서 보기

**ARM** /ɑːrm/ 암 — 1983년 영국 Acorn Computers에서 출발(Acorn RISC Machine). 저전력·저비용에 최적화되어 모바일 시대(스마트폰)를 사실상 독점했습니다. 그러나 철저히 **사유 모델**: ARM Holdings에 설계 라이선스료(수억 원 단위)와 로열티(칩 판매량당 %)를 내야 합니다.

RISC-V는 정확히 이 지점을 공격합니다: **"ARM만큼 좋은 설계 철학을, 로열티 없이."**

| | ARM | RISC-V |
|---|---|---|
| 소유 | ARM Holdings (사기업) | 누구의 것도 아님 (재단이 관리만) |
| 비용 | 라이선스료 + 로열티 | **0원** |
| 명령어 확장 | 계약 위반 (허용 안 됨) | **자유** ← Coral이 필요로 한 것 |
| 생태계 | 매우 성숙 (30년+) | 급성장 중 (10년+) |

> ZCU102의 **PS(Cortex-A53)는 ARM**이고, 우리가 올리는 **Coral은 RISC-V**입니다. 이 프로젝트 자체가 "구세대 사유 ISA와 신세대 개방 ISA가 한 보드 위에서 협력"하는 그림입니다.

## 6.3 모듈식 설계 — 레고 블록 ISA

RISC-V의 설계 철학에서 가장 중요한 결정: **기본(base)은 최소한으로, 나머지는 전부 선택 확장(extension)으로.**

```
                RV32I  ← 기본. 이것만으로 완전한 컴퓨터 (7장)
                  │
     ┌────────────┼────────────┬───────────┬───────────┐
     ▼            ▼            ▼           ▼           ▼
     M            F            A           C          V/Zve
  곱셈나눗셈    부동소수점    원자연산      압축명령    벡터(SIMD)
  (8장)        (실수 계산)  (멀티코어    (코드크기    (병렬 데이터
                            동기화)      절감)        처리)
```

각 확장은 알파벳 한 글자(또는 `Z`로 시작하는 이름)로 표시되고, 이어 붙여 씁니다: `RV32IMAFC` = RV32I + M + A + F + C.

### 왜 이렇게 쪼갰나 — 면적과 용도의 스펙트럼

```
초소형 마이크로컨트롤러 (센서, IoT)
   → RV32I만. 곱셈 거의 안 씀. 회로 최소화가 최우선.
   → LUT 수백 개 수준

범용 임베디드 (우리의 PS급)
   → RV32IMAC. 실용적인 균형.

고성능 애플리케이션 프로세서
   → RV64GC (G = IMAFD 묶음 별칭). 서버·PC급.

AI/신호처리 특화 (Coral)
   → RV32IMF + 벡터 확장(Zve32x) + 커스텀. 용도에 맞춰 조립.
```

하나의 ISA 문서가 마이크로컨트롤러부터 슈퍼컴퓨터까지 커버합니다 — 이것이 산업이 RISC-V로 몰리는 실질적 이유입니다. **부품을 표준화하고, 선택은 자유롭게.**

## 6.4 Zve, Zicsr, Zifencei, Zbb — "Z" 접두사의 정체

**Z 접두사**는 표준 확장이지만 알파벳 한 글자를 새로 배정하기엔 너무 세부적인 기능에 붙습니다. Coral의 ISA 문자열을 다시 봅니다:

```
rv32imf_zve32x_zicsr_zifencei_zbb
```

| 조각 | 발음/읽기 | 뜻 | 왜 필요한가 |
|---|---|---|---|
| `rv32` | 알브이서른둘 | 32비트 주소·레지스터 폭 | Coral의 데이터 폭 선택 |
| `i` | 아이 | 기본 정수 명령 (필수, 7장) | 모든 RISC-V의 뿌리 |
| `m` | 엠 | 곱셈/나눗셈 (8장) | AI 연산에 곱셈은 필수처럼 보이나… (8장 반전) |
| `f` | 에프 | 단정밀도 부동소수점 | 실수 연산(신경망 활성화 함수 등) |
| `zve32x` | 지브이이 서른둘 엑스 | **임베디드용** 벡터 확장, 32비트 요소 폭 | 완전한 V(벡터) 확장은 크고 무거움. 임베디드에 맞게 축소한 버전 |
| `zicsr` | 지아이씨에스알 | 제어·상태 레지스터(CSR) 접근 명령 | 성능 카운터(rdcycle 등, 20장), 인터럽트 상태 제어 |
| `zifencei` | 지아이펜스아이 | 명령 캐시 동기화(`fence.i`) | ITCM에 새 프로그램을 써넣은 뒤, "새로 쓴 코드를 Fetch가 다시 읽게 하라"는 명령. **우리의 M4/M5 코드 적재 직후 필수** |
| `zbb` | 지비비 | 기본 비트 조작(bit manipulation, basic) | 카운트·회전·비트 반전 등 저수준 최적화 명령 |

### zifencei가 왜 우리 프로젝트에 중요한가

ARM이 AXI로 Coral의 ITCM에 새 프로그램(바이너리)을 써넣으면, Coral의 **명령 캐시나 파이프라인 내부 버퍼에 이미 옛 상태가 남아있을 수 있습니다.** `fence.i`는 "지금부터 명령어 스트림을 새로 읽어라"라고 강제하는 명령입니다. 이게 없으면 새로 올린 프로그램이 실행되지 않고 예전 잔상이 도는 버그가 날 수 있습니다. — 19장 main.c의 `Xil_DCacheFlush`가 **데이터** 캐시 문제였다면, `fence.i`는 **명령어** 캐시 문제의 해법이고, 이건 ARM 쪽이 아니라 **Coral 프로그램 자신**이 실행해야 하는 명령입니다(보통 부트스트랩 코드 맨 앞에).

## 6.5 현재 프로젝트 연결

- Coral이 RISC-V를 택한 이유가 6.2절의 "자유" 그 자체 — NPU에 필요한 벡터·행렬 관련 명령을 자유롭게 확장할 수 있습니다.
- ISA 문자열 전체를 이제 완전히 읽을 수 있습니다 — 이게 "README의 모든 문장을 설명할 수 있어야 한다"는 목표의 실제 달성 지점입니다.
- `zve32x`가 SIMD 128비트(17장)의 ISA적 근거이고, `zicsr`이 20장의 성능 실측 도구(rdcycle)의 근거이며, `zifencei`가 M5 소프트웨어 개발에서 실전 함정이 됩니다.

## 요약

- RISC-V는 사유 ISA 생태계의 결핍(교육·연구·산업 자유)에 대한 응답으로 버클리에서 시작, 재단이 관리하는 개방형 표준.
- ARM과의 대비: 로열티 유무, 확장 자유의 유무가 핵심 차이. 우리 보드가 두 철학의 공존 현장.
- 모듈식(base + extension) 설계로 초소형부터 슈퍼컴까지 하나의 ISA로 커버.
- Z 접두사 확장(zve32x, zicsr, zifencei, zbb) 각각의 실용적 역할, 특히 `zifencei`의 실전 중요성.

## 예상 질문

**Q (교수님). "RISC-V가 자유로운 게 오히려 파편화 위험 아닌가?"**
A. 맞는 우려이며 실제 논의 대상입니다. 다만 base ISA(RV32I/RV64I)는 고정되어 있고, 표준 확장은 재단 인증을 거쳐야 공식 명칭을 쓸 수 있어 무분별한 파편화를 어느 정도 억제합니다. 완전 커스텀 명령(비표준)은 별도 인코딩 공간에 격리되어 표준 부분과 충돌하지 않도록 설계돼 있습니다.

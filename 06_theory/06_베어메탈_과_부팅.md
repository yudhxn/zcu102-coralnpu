## 1. 베어메탈이란

**베어메탈(bare-metal)** = **OS 없이** 하드웨어를 직접 제어하는 방식. "맨 쇳덩이 위에서 돈다"는 뜻입니다.

| | 리눅스 (PetaLinux) | **베어메탈** ✅ |
|---|---|---|
| 구조 | OS가 하드웨어를 관리 | **내 프로그램이 하드웨어를 직접** |
| 필요한 것 | 커널, 디바이스 트리, rootfs, 드라이버(.ko) | **C 프로그램 하나** |
| 부팅 | BootROM→FSBL→PMU/ATF→U-Boot→Linux | **BootROM→FSBL→내 앱** |
| 개발 도구 | PetaLinux (리눅스 필요) | **Vitis (윈도우 가능)** |
| 난이도 | 높음 | **낮음** |
| 멀티태스킹 | 가능 | 불가 (필요 없음) |

### 왜 베어메탈로 확정했나

두 근거가 맞물렸습니다.

1. **Coral이 프로세서라서 가능** — 드라이버로 조종할 필요가 없음 (→ `01_coral_npu_구조.md`)
2. **목표 수준이 "input/output만 되면 된다"** — 선배 확인 결과

> **부수 효과**: 리눅스 서버가 불필요해졌습니다. VPN·서버 계정·Vitis 설치 허가를 기다리던 병목이 통째로 사라졌어요. 윈도우 Vivado 2026.1로 진행 가능.

## 2. 베어메탈에서 하드웨어를 다루는 법

베어메탈에서는 **하드웨어 레지스터가 그냥 메모리 주소**입니다. 드라이버라는 중간 계층이 없어요.

```c
#include "xparameters.h"
#include "xil_io.h"

#define CORAL_BASE   XPAR_CORAL_0_BASEADDR   // Address Editor에서 정한 주소

// 개념적 흐름 (실제 레지스터 맵은 Coral 문서 확인 필요)
Xil_Out32(CORAL_BASE + RESET_REG, 1);        // 리셋
memcpy(CORAL_ITCM, program_elf, size);        // 프로그램을 ITCM에 적재
memcpy(DDR_INPUT_BUF, input_data, len);       // 입력 준비
Xil_Out32(CORAL_BASE + START_REG, 1);         // 시작
while (!Xil_In32(CORAL_BASE + DONE_REG));     // 완료 대기 (폴링)
xil_printf("result: %d\n", result);           // UART 출력
```

| 함수 | 하는 일 |
|---|---|
| `Xil_Out32(addr, val)` | 주소에 32비트 값 쓰기 |
| `Xil_In32(addr)` | 주소에서 32비트 값 읽기 |
| `xil_printf(...)` | UART로 출력 (경량 printf) |

**`xparameters.h`**: Vitis가 `.xsa`를 읽어 **자동 생성**하는 헤더. Block Design에서 정한 주소가 `XPAR_*` 매크로로 들어옵니다. 주소를 손으로 적지 않아도 돼요.

**폴링(polling)**: 완료 신호를 계속 확인하며 기다리는 방식. 인터럽트보다 단순해 베어메탈 첫 구현에 적합합니다.

## 3. 부팅 릴레이 (베어메탈 버전)

```
① 전원 ON
      ↓
② BootROM  (칩에 영구 각인, 수정 불가)
      · 부팅 모드 핀 읽기 (SD? JTAG? QSPI?)
      · SD카드에서 BOOT.bin 탐색
      ↓
③ PMU Firmware   ← ⭐ 이게 빠져서 실패했었음
      · 전원 도메인 켜기, 저수준 초기화
      ↓
④ FSBL (First Stage Boot Loader)
      · DDR 메모리 컨트롤러 초기화
      · PL에 비트스트림 로딩 → Coral 회로 탄생
      · 다음 실행할 것을 메모리에 적재
      ↓
⑤ 내 베어메탈 앱 실행    ← 리눅스 자리에 이게 들어감
      · Coral 구동 → UART로 결과 출력
```

**리눅스 방식과 비교**: ATF, U-Boot, 커널, rootfs가 통째로 빠집니다. 단계가 줄어든 만큼 실패 지점도 줄어요.

---

## 4. BOOT.bin 구조

②~⑤의 주자들을 **하나로 묶은 컨테이너 파일**.

```
BOOT.bin ─┬─ PMU firmware   (pmufw.elf)     ← 빠지면 안 됨
          ├─ FSBL           (fsbl.elf)
          ├─ 비트스트림     (system.bit)     ← Coral 하드웨어
          └─ 베어메탈 앱    (app.elf)
```

**bootgen** = 이 조각들을 BOOT.bin으로 묶어주는 Xilinx 도구.
**BIF 파일**(`.bif`) = bootgen에게 주는 **조립 설명서**.

## 5. 7/14 실패 사건 — 직접 찾아낸 원인 ⭐

**이 프로젝트에서 가장 잘한 디버깅입니다. 원리를 기억해두면 M4에서 재발을 막습니다.**

### 증상

```
Xilinx Zynq MP First Stage Boot Loader
Release 2018.3
PMU-FW is not running, certain applications may not be supported.
```
→ 이 3줄 출력 후 **정지**

### 조사 — ITRI의 `SD_BOOT.bif`

```
the_ROM_image:
{
  [fsbl_config] a53_x64
  [bootloader]  ...\SD_BOOT.elf
  [destination_device = pl] ...\zcu102_base_trd_wrapper.bit
}
```

### 발견

> **`[pmufw_image]` 항목이 아예 없음.**

```
BIF에 PMU 펌웨어가 안 적혀 있음
      ↓
BOOT.bin에 PMU 펌웨어가 안 들어감
      ↓
FSBL 배너: "PMU-FW is not running"
      ↓
Rev 1.1 보드에서 부팅 정지
```

### 왜 이게 좋은 디버깅인가

**로그의 경고 문구와 설정 파일의 내용이 정확히 대응한다**는 것을 짚어냈습니다.

- 로그: "PMU-FW is not running" ← **증상**
- `.bif`: `[pmufw_image]` 없음 ← **원인**

설명서에 부품이 안 적혀 있으니 그 부품이 안 들어간 것. 단순하지만 **실물 증거로 확정**한 진단입니다.

> ⚠️ **주의**: 초기에는 "2018.3 FSBL ↔ Rev 1.1 보드 버전 불일치"로 **추정**했었습니다. 방향은 맞았지만 정확한 원인은 `.bif`를 직접 열어본 뒤에야 나왔어요. **추정과 확정을 구분해서 기록**한 것이 LOG.md의 좋은 점입니다.

### 검증

AMD 공식 2019.1 프리빌트 이미지로 부팅 → **로그인 프롬프트까지 정상**

```
커널 4.19 aarch64 / nproc=4 / FPGA state=operating
```

→ 보드·SD·UART·스위치 **전부 정상**. 순수 소프트웨어 문제로 확정.

### M4에 적용할 교훈

> **BOOT.bin을 만들 때 `.bif`에 `[pmufw_image]`를 반드시 포함할 것.**

```
the_ROM_image:
{
  [fsbl_config] a53_x64
  [bootloader]  fsbl.elf
  [pmufw_image] pmufw.elf          ← ⭐ 절대 빠뜨리지 말 것
  [destination_device = pl] system.bit
  [destination_cpu = a53-0] app.elf
}
```

## 6. `.hdf` / `.xsa` 형식 문제 — 이미 해소됨

```
.hdf  →  2019.1 이하 하드웨어 정보 파일
.xsa  →  2019.2 이상 (형식 변경)

Vivado 2026.1은 .hdf 미지원
```

당시엔 "구버전 Vivado를 설치해야 하나" 하는 문제였지만,

> **M4에서 Block Design을 새로 만들어 `.xsa`를 직접 생성**하므로 ITRI의 `.hdf`는 더 이상 필요 없습니다. 구버전 설치 문제는 자연히 사라졌어요.

## 7. 보드 접속 환경 (검증 완료)

| 항목 | 설정 |
|---|---|
| 부팅 모드 | **SW6: 1-ON, 2/3/4-OFF** (SD 부팅) |
| UART | **J83, 115200 8N1** |
| 포트 | **CP2108 Interface 0** |

### ⚠️ COM 포트 함정

```
CP2108 Interface 0~3 → COM6 / COM3 / COM4 / COM5
                        ↑
                    Interface 0 = COM6
```

> **가장 낮은 COM 번호가 아닙니다.** 장치 관리자에서 **"Interface 0"** 이라고 적힌 것을 골라야 해요. COM3을 골라 아무것도 안 나오는 게 흔한 함정입니다.

**115200 8N1** = 초당 115200비트, 데이터 8비트, 패리티 없음(None), 정지비트 1.

### 참고 — SSH (리눅스 이미지로 부팅했을 때)

베어메탈에서는 안 쓰지만 기록해둡니다.

```bash
ssh -o HostKeyAlgorithms=+ssh-rsa root@10.126.37.57
```

보드의 Dropbear(2019년판)가 `ssh-rsa`만 지원하는데 최신 OpenSSH가 이를 거부해서 옵션이 필요했습니다.

**VS Code Remote-SSH는 불가** — 보드 리눅스가 BusyBox라 `tar --no-same-owner`, `wget --no-config`를 지원하지 않아 VS Code 서버 설치가 실패합니다. 임베디드 보드에는 구조적으로 안 붙어요. 순수 SSH 터미널은 정상.

**BusyBox** = 임베디드용으로 여러 명령어를 하나로 합친 경량 도구 모음. 옵션이 제한적입니다.

# 05. AXI4와 M4 설계 (🚧 현재 단계)

← [목차](00_INDEX.md) | 이전: [04. 합성 결과 읽는 법](04_합성결과_읽는법.md)

---

## 1. AXI4란

**AXI4** = ARM이 만든 **칩 내부 버스 규격**. 블록끼리 데이터를 주고받는 약속입니다.

**버스**를 도로에 비유하면, AXI는 그 도로의 **교통 법규**예요. 서로 다른 회사가 만든 블록이라도 이 규약만 지키면 연결됩니다. Coral(구글)과 Zynq PS(Xilinx)를 이을 수 있는 이유가 이것입니다.

## 2. manager / subordinate

| 역할 | 하는 일 |
|---|---|
| **manager** (구 master) | **요청하는 쪽.** "이 주소 읽어줘", "여기 써줘" |
| **subordinate** (구 slave) | **응답하는 쪽.** 요청받아 처리 |

> 문서마다 master/slave와 manager/subordinate가 섞여 있는데 같은 것입니다. Coral 포트 이름은 `io_axi_slave_*`, `io_axi_master_*`로 구 표기를 씁니다.

## 3. AXI4의 5채널 구조

AXI는 읽기와 쓰기가 **독립된 채널**로 분리돼 있습니다.

| 채널 | 이름 | 방향 | 내용 |
|---|---|---|---|
| **AW** | Write Address | M→S | "어디에 쓸 것이다" |
| **W** | Write Data | M→S | 실제 쓸 데이터 |
| **B** | Write Response | S→M | "다 썼다" 응답 |
| **AR** | Read Address | M→S | "어디를 읽겠다" |
| **R** | Read Data | S→M | 읽은 데이터 |

**왜 나눠놨나**: 주소와 데이터가 분리돼 있어 **주소를 먼저 여러 개 보내놓고** 데이터를 나중에 받을 수 있습니다. 읽기와 쓰기도 동시에 진행돼요. 이걸 **파이프라이닝**이라 하고, 대역폭이 크게 올라갑니다.

> 신호가 2,866개나 되는 이유가 이겁니다. 5채널 × (주소·데이터·제어·핸드셰이크) × 128비트 데이터 폭.

### 핸드셰이크

모든 채널은 **VALID / READY** 두 신호로 동기를 맞춥니다.

```
VALID (보내는 쪽): "줄 것이 준비됐다"
READY (받는 쪽):   "받을 준비가 됐다"
        ↓
둘 다 1인 클럭에서 전송 성립
```

**의의**: 어느 쪽이든 느리면 기다려줍니다. 속도가 다른 블록끼리 안전하게 이을 수 있어요.

## 4. PS ↔ PL 연결 구조

```
┌──────────────── ZCU102 (XCZU9EG) ────────────────┐
│                                                   │
│  PS (ARM Cortex-A53)        PL (FPGA)             │
│                                                   │
│  M_AXI_HPM0 ──────────────→ io_axi_slave          │
│   "일 시키기"                (설정·시작 명령)      │
│                                                   │
│  S_AXI_HP0  ←────────────── io_axi_master         │
│   "메모리 빌려주기"          (데이터 읽고 쓰기)    │
│                                                   │
│  베어메탈 앱                 CoreMiniAxi           │
│   · input 주입                · scalar / vector    │
│   · 결과 수신                 · matrix             │
│   · UART 출력                                      │
└───────────────────────────────────────────────────┘
```

### 포트 이름 읽는 법

| 포트 | 풀네임 | 누가 주도 | 용도 |
|---|---|---|---|
| **M_AXI_HPM0** | Master AXI High Performance Master 0 | **PS** | PS가 PL의 레지스터를 읽고 씀 |
| **S_AXI_HP0** | Slave AXI High Performance 0 | **PL** | PL이 PS 쪽 DDR에 접근 |

**핵심은 방향입니다.** `M_`은 PS가 요청하는 포트, `S_`는 PS가 응답하는 포트예요. 누가 주도권을 쥐느냐로 이름이 갈립니다.

### 왜 둘 다 필요한가

```
M_AXI_HPM0 만 있으면
  → ARM이 Coral에게 데이터를 일일이 떠먹여야 함. 느리고 ARM이 놀지 못함

S_AXI_HP0 만 있으면
  → Coral에게 "시작해"라고 말할 방법이 없음

둘 다 있어야
  → ARM: "이 주소에 입력 있다, 시작해"  (한 번만 말하면 됨)
  → Coral: 스스로 DDR에서 데이터를 끌어다 계산
```

### 폭 정합 ⭐

```
Coral io_axi_*  : data 128b
ZCU102 HP 포트  : data 128b
        ↓
   폭 일치 → 변환 로직 불필요
```

폭이 다르면 **AXI Data Width Converter** IP를 끼워야 하고, 자원·지연·복잡도가 모두 늘어납니다. 이게 맞아떨어진 건 유리한 조건이에요.

## 5. Block Design

**Block Design** = Vivado에서 블록을 배치하고 선으로 잇는 **GUI 방식 설계**.

> 신호 2,866개를 손으로 이으라면 불가능합니다. Block Design은 AXI 연결을 **자동으로 생성**해줘요. `Run Connection Automation`을 누르면 인터커넥트와 클럭·리셋 배선을 알아서 만듭니다.

### M4 작업 순서

```
1. Vivado Block Design 생성
     · Zynq UltraScale+ MPSoC IP 추가
     · CoreMiniAxi를 모듈로 추가

2. PS 설정
     · M_AXI_HPM0 활성화
     · S_AXI_HP0 활성화
     · PL 클럭 출력 활성화

3. 연결
     · PS M_AXI_HPM0 → Coral io_axi_slave
     · Coral io_axi_master → PS S_AXI_HP0
     · 클럭·리셋 연결

4. Address Editor에서 주소 할당
     · Coral 레지스터가 ARM에서 보일 주소 확정
     ⭐ 이 주소가 베어메탈 코드에 그대로 들어감

5. Synthesis → Implementation → Generate Bitstream

6. .xsa 내보내기 (Export Hardware, bitstream 포함)

7. Vitis 베어메탈 앱 작성
8. bootgen으로 BOOT.bin 생성
```

### 4단계를 특히 주의

**Address Editor**에서 정한 주소가 곧 베어메탈 코드의 `CORAL_BASE`가 됩니다. 여기를 기록해두지 않으면 나중에 코드에서 헤맵니다.

## 6. Synthesis vs Implementation ⚠️

**M4에서 새로 등장하는 위험입니다.**

| 단계 | 하는 일 | 판정하는 것 |
|---|---|---|
| **Synthesis** | 코드 → 논리 게이트 그물망 | **"자원이 충분한가"** (M3에서 통과 ✅) |
| **Implementation** | 실제 LUT에 **배치**하고 선을 **연결** | **"타이밍이 맞는가"** |

> **합성 통과 ≠ 구현 통과.** M3의 18%는 "들어간다"는 뜻이지 "동작한다"는 뜻이 아닙니다.

### 타이밍 위반이란

```
클럭 주기 = 10ns (100MHz)
신호가 A에서 B까지 가는 데 걸리는 시간 = 12ns
        ↓
다음 클럭이 왔는데 신호가 아직 도착 안 함
        ↓
잘못된 값을 읽음 → 회로 오동작
```

이걸 **타이밍 위반(timing violation)**, 리포트에서는 **음수 슬랙(negative slack)** 으로 표시됩니다.
**슬랙(slack)** = 여유 시간. 양수면 통과, 음수면 위반.

### 대응 순서 (쉬운 것부터)

| 순서 | 방법 | 비고 |
|---|---|---|
| 1 | **클럭 주파수 낮추기** | **가장 빠른 해결.** 100MHz → 50MHz 등. 성능 목표가 "동작하면 된다"이므로 충분히 허용 가능 |
| 2 | Implementation 전략 변경 | Vivado의 `Performance_*` 프리셋 시도 |
| 3 | 임계 경로 파악 후 파이프라인 추가 | 어려움. 마지막 수단 |

> **이 프로젝트의 목표 수준은 "input/output만 되면 된다"** 입니다. 타이밍이 안 맞으면 **주저 없이 클럭을 낮추세요.** 주파수를 지키려다 시간을 버리는 게 더 큰 손해입니다.

> **DSP 미사용과의 연결**: 곱셈이 LUT로 구현돼 있어(→ `04_합성결과_읽는법.md`) 곱셈 경로가 길 가능성이 있습니다. 타이밍 위반이 나면 이 경로가 임계 경로로 잡힐지 확인해볼 만합니다. M6 분석의 근거 자료가 돼요.

## 7. M4 체크포인트

| # | 확인 항목 | 통과 기준 |
|---|---|---|
| 1 | Block Design 연결 | Validate Design 오류 없음 |
| 2 | 주소 할당 | Address Editor에 Coral 주소 확정·기록 |
| 3 | Synthesis | 자원 여유 확인 (IOB 경고 사라졌는지) |
| 4 | Implementation | **슬랙 양수** (음수면 클럭 하향) |
| 5 | Bitstream | 생성 성공 |
| 6 | .xsa 내보내기 | bitstream 포함 확인 |
| 7 | BOOT.bin | **`[pmufw_image]` 반드시 포함** (→ `06_베어메탈_과_부팅.md`) |
| 8 | 보드 부팅 | UART로 앱 배너 확인 |
| 9 | Coral 인식 | 레지스터 read/write 왕복 성공 |

**9번이 M4의 진짜 목표**입니다. Coral 레지스터에 값을 쓰고 다시 읽어 같은 값이 나오면 **AXI 연결이 살아 있다**는 증명이에요. 여기까지가 M4 완료.

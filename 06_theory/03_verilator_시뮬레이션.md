## 1. Verilator란

**Verilator** = Verilog로 기술된 회로를 **PC에서 소프트웨어로 흉내내어 실행**하는 도구.

정확히는 Verilog를 **C++ 코드로 번역**한 뒤 컴파일해 돌립니다. 그래서 다른 시뮬레이터보다 훨씬 빨라요.

## 2. 왜 시뮬레이션을 먼저 하는가

| | 시뮬레이션 | 실제 보드 |
|---|---|---|
| 준비 시간 | 빌드 몇 분 | 합성+구현 수십 분~수 시간 |
| 내부 관찰 | **모든 신호를 볼 수 있음** | 관찰 지점이 제한적 |
| 오류 원인 파악 | 쉬움 | 어려움 (안 되면 왜 안 되는지 안 보임) |
| 진짜 검증 | 아님 | 맞음 |

> **원칙**: 비트스트림을 굽는 건 비쌉니다. **"논리가 맞나"는 시뮬에서 먼저** 끝내고, 보드는 "실제로도 되나"를 확인하는 데 씁니다.

## 3. M2 결과 — 무엇이 증명되었나

```
bazel build //tests/verilator_sim:core_mini_axi_sim      (368초)

로그: core_mini_axi_cc_library_emit_verilog
Verilator: 124 modules, 1.592 MB sources

실행 → "Simulation stopped by user"  (core dump 없음, 정상 종료)
```

### 이 세 줄이 증명하는 것

| 관찰 | 의미 |
|---|---|
| `emit_verilog` 로그 | **Chisel → Verilog 변환이 실제로 수행됨** |
| 124 modules / 1.592 MB | **합성에 넣을 재료가 확보됨** |
| core dump 없이 정상 종료 | **RTL이 RISC-V 바이너리를 진짜로 실행함** |

> **가장 중요한 건 세 번째**입니다. 코드가 빌드되는 것과 **동작하는 것**은 다릅니다. 시뮬레이터가 크래시 없이 끝났다는 건 설계가 논리적으로 살아 있다는 뜻이에요.

**core dump** = 프로그램이 비정상 종료하며 메모리 상태를 덤프하는 것. 없다 = 정상 종료.

## 4. 안전망으로서의 가치 ⭐

마감(08-31)이 있는 프로젝트에서 이 항목은 실질적으로 중요합니다.

```
최선:  보드에서 input → 추론 → output 동작        (M5 목표)
차선:  합성까지 성공 + 리소스 분석                 (M3에서 이미 확보 ✅)
최소:  시뮬레이션 기반 검증 + 사이클 측정 + 분석   (M2에서 이미 확보 ✅)
```

**즉 M4·M5가 막혀도 제출할 결과물은 이미 손에 있습니다.** 이건 심리적으로도, 일정 관리 측면에서도 큰 차이예요. 남은 기간을 "실패하면 끝"이 아니라 "더 올릴 수 있으면 올린다"로 쓸 수 있습니다.

> 저장소 README의 "완화 요소"에 이 내용이 적혀 있는데, 정확한 판단입니다.

## 5. 삽질 기록 — Bazel 출력 경로 문제

**LOG.md에 기록된 실제 사건.** 원리를 알아두면 재발 시 바로 해결됩니다.

### 증상

하나를 빌드하면 다른 하나가 `No such file or directory`로 사라짐.

### 원인 1 — 타깃이 다르면 출력 폴더가 갈린다

```
examples (RISC-V 타깃)   → bazel-out/k8-fastbuild-ST-dd8dc713f32d/
verilator_sim (x86 타깃) → bazel-out/k8-fastbuild/
```

**왜 다른가**: 두 빌드는 **컴파일 설정이 다른 별개의 빌드**입니다.

- `examples` → Coral에서 돌 **RISC-V 바이너리** (크로스 컴파일)
- `verilator_sim` → PC에서 돌 **x86 시뮬레이터**

Bazel은 설정이 다르면 결과물을 **다른 폴더에 격리**합니다. 섞이면 잘못된 바이너리를 링크할 수 있으니까요. 뒤의 해시(`ST-dd8dc713f32d`)가 그 설정을 식별하는 값입니다.

> **이건 버그가 아니라 Bazel의 안전장치입니다.**

### 원인 2 — `bazel-bin`은 심볼릭 링크다

**심볼릭 링크(symlink)** = 실제 파일을 가리키는 바로가기.

```
bazel-bin  →  (가장 최근 빌드의 출력 폴더)
```

빌드할 때마다 **목적지가 바뀝니다.** A를 빌드하면 A쪽을 가리키고, B를 빌드하면 B쪽으로 옮겨가요. 그래서 `bazel-bin/...` 경로로 저장해둔 A의 위치가 갑자기 "없는 파일"이 됩니다.

### 해결

```bash
# ~/.bashrc — 절대 경로로 고정
export SIM=/home.../bazel-out/k8-fastbuild/bin/tests/verilator_sim/...
export ELF=/home.../bazel-out/k8-fastbuild-ST-dd8dc713f32d/bin/examples/...
export RTL=...
```

**교훈**: **움직이는 바로가기에 의존하지 말고 실제 경로를 잡는다.**

`~/.bashrc`는 터미널을 열 때마다 자동 실행되는 설정 파일이라, 여기 등록하면 매번 타이핑할 필요가 없습니다.

## 6. 후속 과제

README의 M2 항목은 "Verilator 시뮬에서 Coral 실행 **+ 사이클 측정**"입니다.

- **실행** ✅ 완료
- **사이클 측정** — 명시적 기록이 아직 안 보임

**사이클 측정**이란 "이 연산에 클럭이 몇 번 걸리나"를 세는 것. M6의 성능 분석에서 **기준선(baseline)** 이 됩니다.

> 시뮬레이션 사이클 수는 보드 실측과 비교할 수 있는 유일한 사전 데이터예요. M4가 막힐 경우엔 이 수치 자체가 주요 결과물이 되므로, 여유 있는 지금 확보해두면 보험이 됩니다.

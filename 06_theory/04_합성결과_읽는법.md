## 1. 합성 조건

| 항목 | 값 |
|---|---|
| 도구 | Vivado 2026.1 (Windows) |
| 타깃 칩 | `xczu9eg-ffvb1156-2-e` (ZCU102 Evaluation Board) |
| **Top module** | **CoreMiniAxi** |
| 소스 | `CoreMiniAxi.sv` **단일 파일** (36,725줄 / 1.6MB) |
| Verilog define | **`SYNTHESIS`** |

### Top module이 전략의 핵심

**Top module(최상위 모듈)** = 회로의 바깥 껍데기가 될 모듈.

여기서 **SoC 전체가 아닌 NPU 코어(CoreMiniAxi)만** 최상위로 잡은 것이 이번 성공의 결정적 판단이었습니다. (→ 4절 참조)

### ⚠️ 단일 파일이어야 하는 이유

`CoreMiniAxi.sv` 안에 `ClockGate`, `RstSync`, `Sram`이 **이미 내장**되어 있습니다.

```
hdl/verilog/ 의 같은 이름 파일을 함께 추가
        ↓
module redefinition (모듈 중복 정의) 오류
```

**같은 이름의 모듈이 두 번 정의되면** 합성기는 어느 쪽을 쓸지 판단할 수 없어 에러를 냅니다. 부품 파일을 "혹시 필요할까 봐" 넣으면 오히려 실패해요.

## 2. `SYNTHESIS` define이 성패를 갈랐다 ⭐

**Verilog define** = 컴파일 시점에 "이 코드 경로로 가라"고 지시하는 스위치. C의 `#ifdef`와 같은 개념.

| define | SRAM 구현 방식 | 합성 |
|---|---|---|
| **정의함** ✅ | 동작 기술 메모리 `bit [127:0] mem[...]` | **BRAM으로 추론됨** |
| 정의 안 함 | **DPI-C 기반 시뮬 전용 메모리** | ❌ **합성 불가** |

### DPI-C가 왜 합성 불가인가

**DPI-C** = Direct Programming Interface for C. **Verilog가 C 함수를 호출하는 통로.**

```
시뮬레이터(PC):  Verilog → C 함수 호출 → C 코드가 PC에서 실행됨  ✅
FPGA:            Verilog → C 함수 호출 → ??? 
                 FPGA 안에는 C를 실행할 것이 없음                 ❌
```

FPGA는 **논리 게이트의 집합**입니다. C 프로그램을 돌릴 운영체제도 프로세서도 없어요. 그래서 DPI-C를 쓴 코드는 물리적으로 회로가 될 수 없습니다.

### BRAM 추론(inference)이란

**추론(inference)** = 합성기가 코드를 보고 "이건 메모리네" 하고 **알아서 전용 하드웨어에 매핑**하는 것.

```verilog
bit [127:0] mem [0:255];   // 이렇게 쓰면
```
→ 합성기가 "128비트 × 256개 배열 = 메모리" 로 인식 → **BRAM 블록에 배치**

LUT로 만들면 엄청난 자원을 먹지만, BRAM은 이 용도로 만들어진 전용 블록이라 효율적입니다.

### 정의하면 안 되는 것

```
USE_TSMC12FFC / USE_GF12LPP / USE_GF22   ← 정의 금지
```

TSMC, GlobalFoundries 등 **실제 반도체 공장의 공정 전용 매크로**입니다. 그 공정의 SRAM 매크로 셀을 부르는 코드라 FPGA에는 존재하지 않아요.

> **정리**: Coral의 SRAM 코드는 **① 시뮬용(DPI-C) ② 실칩용(공정 매크로) ③ 합성용(동작 기술)** 세 갈래이고, FPGA는 ③으로 가야 합니다. 그 스위치가 `SYNTHESIS`입니다.

## 3. 리소스 사용량 — 숫자 해석

| 자원 | 사용 | 가용 | 비율 | 역할 |
|---|---|---|---|---|
| **CLB LUT** | ~49,300 | 274,080 | **~18%** | 논리 연산 |
| **Register** | ~8,930 | 548,160 | ~1.6% | 값 저장 (플립플롭) |
| **Block RAM** | 10 | 912 | 1.10% | 내장 메모리 |
| **DSP48E2** | 6 | 2,520 | 0.24% | 전용 곱셈-누적기 |
| **BUFGCE** | 3 | 116 | 2.59% | 클럭 분배 버퍼 |

### 해석 ① LUT 18% — 넉넉히 들어감

사전 리스크였던 "6배 차이라 수용 불가"가 **정량적으로 해소**되었습니다. M4에서 PS 연결 로직과 AXI 인터커넥트가 추가돼도 여유가 충분해요.

**LUT** = Look-Up Table. 임의의 논리 함수를 표로 흉내내는 FPGA 기본 부품.

### 해석 ② BRAM 10개 — 사양과 일치 ✅

```
ITCM 8KB + DTCM 32KB = 40KB
BRAM 10개 ≈ 그 정도 용량
```

**데이터시트 사양과 합성 결과가 맞아떨어짐** → **설계대로 합성됐다는 교차 검증**입니다. 이런 확인은 "빌드는 됐는데 엉뚱한 게 만들어진" 상황을 걸러줘요.

### 해석 ③ DSP 6개 — 이상 신호 ⚠️

**가장 주목할 항목입니다.**

```
행렬 연산이 핵심인 NPU인데 곱셈기를 6개만 사용?
LUT6는 25,975개 사용
        ↓
곱셈이 DSP48E2가 아니라 LUT로 구현된 것으로 보임
```

**DSP48E2** = Xilinx FPGA의 전용 곱셈-누적 회로. 곱셈에 특화돼 LUT보다 훨씬 빠르고 자원 효율이 좋습니다.

**추정 원인**: `USE_GENERIC` 경로의 영향. 특정 벤더에 종속되지 않는 **일반(generic) 구현**을 쓰면, 합성기가 벤더 전용 블록(DSP) 대신 범용 논리(LUT)로 만들어버립니다.

**왜 문제인가**
- LUT 곱셈은 DSP보다 **느리고** 자원을 많이 씀
- 최대 동작 주파수가 낮아질 수 있음 → M4 타이밍에 영향 가능

**왜 기회인가**
- **M6 분석 항목**으로 이미 기록해두신 게 정확한 판단입니다
- "왜 DSP를 안 썼는가, 쓰게 하면 어떻게 달라지는가"는 **깊이 있는 분석 소재**예요
- 데모에서 나올 법한 질문에 대한 답을 미리 준비하는 셈

> 이건 **약점이 아니라 결과물**입니다. 발견하고 원인을 규명한 것 자체가 분석 역량의 증거예요.

## 4. 리스크가 왜 기우였나 ⭐

```
사전 우려
  합성 타깃 xcvu13p ≈ 3,780K 로직셀
  ZCU102 ZU9EG      ≈   600K 로직셀
  → 6배 이상 차이 → 수용 불가 예상
        ↓
실제
  그 타깃은 SoC 전체 기준이었음
  (UART, I2C, ISP, ROM, 버스 전부 포함)
        ↓
NPU 코어(CoreMiniAxi)만 분리 → LUT 18%
```

### 교훈

> **"칩 전체 크기"와 "내가 필요한 부분의 크기"는 다르다.**

남의 프로젝트 설정값(`part = xcvu13p-...`)을 그대로 자기 상황에 대입하면 과대 추정하게 됩니다. 그 설정이 **무엇을 합성하기 위한 것인지**를 봐야 해요.

**이 판단이 프로젝트를 살렸습니다.** "6배 차이니까 불가능"으로 결론냈다면 여기서 멈췄을 겁니다. 대신 **범위를 좁혀 실측**했고, 결과가 우려를 뒤집었어요.

## 5. Bonded IOB 873.78% — 왜 무시해도 되는가

**IOB** = Input/Output Block. 칩 바깥 **물리적 핀**에 연결되는 블록. ZCU102는 **328개**.

```
현재 (M3)
  CoreMiniAxi를 최상위로 단독 합성
  → AXI 신호 2,866개가 "칩 밖으로 나가는 선"으로 해석됨
  → 328개 핀에 2,866개 필요 → 873.78%
        ↓
M4 이후
  PS(ARM)와 AXI로 내부 연결
  → 신호들이 칩 내부 배선이 됨
  → IOB를 아예 소비하지 않음
```

**비유**: 지금은 건물 방 하나만 떼어놓고 "이 방의 배선이 전부 건물 밖으로 나가야 한다"고 계산한 상황입니다. 실제로는 옆방(PS)과 연결될 배선이에요.

> **결론: 별도 조치 불필요.** M4에서 자연히 해소됩니다.

## 6. 포트 구조 (M4 설계 근거)

| 포트 | 내용 |
|---|---|
| `io_aclk` / `io_aresetn` | **단일 클럭 + 단일 리셋** → 설계 단순 |
| `io_axi_slave_*` | addr 32b / **data 128b** ← PS가 Coral 제어 |
| `io_axi_master_*` | addr 32b / **data 128b** → Coral이 메모리 접근 |

⭐ **결정적 사실**: ZCU102의 **HP 포트도 128비트** → **폭 일치** → **데이터 폭 변환 로직 불필요.**

폭이 다르면 변환 IP를 넣어야 하고, 자원·지연·복잡도가 다 늘어납니다. 이 부분이 맞아떨어진 건 운이 좋은 축이에요.

> **단일 클럭의 이점**: 클럭 도메인이 여러 개면 신호가 넘어갈 때 CDC(Clock Domain Crossing) 처리가 필요해 설계가 크게 어려워집니다. 하나면 그 문제가 없어요.
